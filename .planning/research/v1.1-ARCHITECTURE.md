# Architecture Research: v1.1 "Make It Shine" Integration

**Domain:** Visual effects, Stripe payment, and demo mode integration into existing photo frame slideshow
**Researched:** 2026-02-15
**Confidence:** HIGH -- based on complete codebase reading (all source files reviewed) and well-established CSS/JS patterns

---

## Executive Summary

The v1.1 features fall into three architectural categories:

1. **CSS-layer visual effects** (Ken Burns, blurred backgrounds, overlays) -- integrate into the frontend slideshow DOM/CSS only, zero backend changes
2. **Backend service additions** (demo mode, Stripe) -- new Express routes, new data sources
3. **Bug fixes** -- targeted changes to existing modules

The critical architectural constraint is the **A/B image swap pattern** in `slideshow.html`. Every visual effect must be duplicated per-slot and cleaned up on transition. The existing pattern already handles blob URL revocation and DOM cleanup -- the new effects must hook into that same lifecycle.

## Current Architecture (As-Built from Source)

### Frontend: slideshow.html (1107 lines)

The slideshow is NOT a strict two-element A/B swap. It is a **dynamically-created element** pattern:

```
Current flow:
1. createPhotoElement() -- creates new <img class="photo preload">
2. Fetches /api/photo/random, creates blob URL, sets img.src
3. showSinglePhoto(img) or showDualPortraits(img1, img2):
   a. Removes old non-active, non-preload photos (cleanup stale)
   b. Appends new img to #slideshow
   c. setTimeout(50ms): remove .active from all, add .active to new, remove .preload
   d. setTimeout(1500ms): remove all .photo:not(.active) elements, revoke blob URLs
```

**Key insight:** There are NOT permanent A and B elements. Elements are created, appended, transitioned, then removed after 1.5s. This means visual effects cannot be permanently attached to fixed DOM elements -- they must be created and destroyed per-photo, just like the img elements themselves.

### DOM Structure (Current)

```html
<body>
  <div id="loading">...</div>
  <div id="error">...</div>
  <div id="slideshow">
    <!-- Dynamically created per transition: -->
    <img class="photo active" src="blob:..." />
    <!-- Briefly during transition: -->
    <img class="photo preload" src="blob:..." />
  </div>
  <!-- Fixed overlays (controls, indicators) at z-index 50-100 -->
  <div id="onThisDayIndicator">...</div>   <!-- z-index: 50 -->
  <div id="controls">...</div>              <!-- z-index: 100 -->
  <div id="intervalControls">...</div>      <!-- z-index: 100 -->
  <div id="displayModeControls">...</div>   <!-- z-index: 100 -->
  <div id="info">...</div>                  <!-- z-index: 100 -->
</body>
```

### Backend: Express Route Map

```
/auth/login          GET   -- OAuth redirect
/auth/callback       GET   -- OAuth callback
/auth/status         GET   -- Auth check (JSON)
/auth/logout         POST  -- Clear session
/api/picker/start    POST  -- Create Picker session
/api/picker/status   GET   -- Poll Picker session

/api/config          GET   -- Read config
/api/config          POST  -- Update config
/api/feedback        POST  -- Submit feedback (multipart)
```

### Config System (config.js)

Config has an allowlist validation pattern. Only keys defined in `defaults` are accepted. Current defaults:

```javascript
const defaults = {
  interval: 30,
  displayMode: 'cover',
  onThisDay: false,
  portraitPairs: false,
};
```

Adding new toggleable features requires:
1. Add key to `defaults` in `config.js`
2. Add toggle row in `settings.html`
3. Read in `slideshow.html` via `window.appConfig`

## Feature 1: Ken Burns Effect

### What It Is

A slow zoom-and-pan CSS animation applied to each photo during its display time. Creates a cinematic "documentary" feel. Named after the documentary filmmaker's signature technique.

### Integration Architecture

**Approach: CSS `@keyframes` animation applied per-photo element.**

Each dynamically created `<img>` gets a CSS animation when it becomes `.active`. The animation runs for the duration of the slideshow interval, providing continuous subtle motion.

#### CSS Layer

```css
/* Ken Burns effect -- applied conditionally via JS class */
@keyframes kenburns-1 {
  0%   { transform: scale(1.0) translate(0, 0); }
  100% { transform: scale(1.15) translate(-2%, -1%); }
}

@keyframes kenburns-2 {
  0%   { transform: scale(1.15) translate(-2%, -1%); }
  100% { transform: scale(1.0) translate(1%, 2%); }
}

@keyframes kenburns-3 {
  0%   { transform: scale(1.0) translate(1%, 1%); }
  100% { transform: scale(1.1) translate(-1%, 2%); }
}

/* ... several variants for visual variety */

.photo.kenburns {
  will-change: transform;
  animation-timing-function: linear;
  animation-fill-mode: forwards;
}
```

#### JS Integration Point: `createPhotoElement()` and `showSinglePhoto()`

```
In showSinglePhoto(img):
  After img.classList.add('active'):
    if (kenBurnsEnabled) {
      const variant = randomKenBurnsVariant();
      img.classList.add('kenburns');
      img.style.animationName = variant;
      img.style.animationDuration = currentIntervalSeconds + 's';
    }
```

#### Critical Considerations

1. **`overflow: hidden` on `#slideshow`:** Ken Burns zooms scale the image past its container bounds. The `#slideshow` container MUST have `overflow: hidden` to prevent scrollbars or visual bleed. Currently `#slideshow` is `position: relative; width: 100%; height: 100%` -- add `overflow: hidden`.

2. **`will-change: transform`:** Promotes the element to its own compositor layer, preventing repaints during animation. Essential for smooth 60fps on iPad Pro 1st Gen (A9X chip). Without this, CSS transforms cause full repaints.

3. **Interaction with `object-fit: cover`:** The `transform: scale()` works correctly on elements with `object-fit: cover` -- it scales the entire element including its rendered content. The zoom will slightly increase the crop, which is the desired cinematic effect.

4. **Interaction with opacity transition:** The existing `transition: opacity 1s ease-in-out` for crossfade works independently of `animation` for transform. These do not conflict -- opacity transitions and transform animations can run simultaneously.

5. **Dual portrait mode:** When showing two portraits side-by-side, each gets its own Ken Burns animation (potentially different variants for visual interest). Both images are created independently via `createPhotoElement()`.

6. **Cleanup:** No special cleanup needed. When the photo element is removed from DOM after transition, its animation is automatically destroyed. Blob URL revocation already handles the image data.

7. **Memory on iPad:** CSS animations via `will-change: transform` use GPU compositor layers. Each photo gets one layer (~8-16MB for 2048x1536). With at most 2 images in DOM simultaneously (old fading out, new fading in), this is 16-32MB GPU memory -- well within iPad Pro A9X's 4GB.

#### Config Integration

- New config key: `kenBurns: false` (default off)
- Settings toggle: "Ken Burns" under Visual Effects section
- Read in slideshow: `kenBurnsEnabled = window.appConfig.kenBurns === true`

## Feature 2: Blurred Background Fill

### What It Is

Instead of black bars when a photo doesn't fill the screen (particularly in `contain` mode, or with aspect-ratio mismatches in `cover` mode), display a blurred, scaled-up version of the same photo behind it. This creates a "content-aware" fill similar to what Instagram and YouTube use for portrait videos in landscape players.

### Integration Architecture

**Approach: For each photo, create a paired background `<div>` with the same blob URL as a CSS background-image, plus `filter: blur()` and `transform: scale()`.**

#### New DOM Structure per Photo

```
Current (single photo):
  <img class="photo active" src="blob:..." />

With blurred background:
  <div class="photo-wrapper active">
    <div class="photo-bg" style="background-image: url(blob:...)"></div>
    <img class="photo" src="blob:..." />
  </div>
```

This is the most significant architectural change: replacing bare `<img>` elements with wrapper `<div>` elements that contain both the blurred background and the actual photo.

#### Alternative: Pseudo-element Approach (Simpler but Limited)

Using `::before` pseudo-element on the img is NOT possible because `<img>` elements cannot have pseudo-elements (they are replaced elements in CSS spec). The wrapper div approach is necessary.

#### Alternative: Duplicate `<img>` Without Wrapper (Considered, Rejected)

Could place two separate `<img>` elements side by side in `#slideshow`:
```html
<img class="photo-bg" src="blob:..." />  <!-- blurred background -->
<img class="photo active" src="blob:..." />  <!-- actual photo -->
```

Problem: The current cleanup logic selects `.photo:not(.active)` and removes them. Adding a non-`.photo` class for the background would work, but the elements would not be semantically grouped. If a transition partially fails, orphaned background elements could accumulate.

**Recommendation: Wrapper div approach.** Grouping background + photo in a wrapper makes cleanup atomic -- removing the wrapper removes both elements. This is the cleanest integration with the existing cleanup pattern.

#### CSS Layer

```css
.photo-wrapper {
  position: absolute;
  top: 0;
  left: 0;
  width: 100%;
  height: 100%;
  opacity: 0;
  transition: opacity 1s ease-in-out;
  overflow: hidden;
}

.photo-wrapper.active {
  opacity: 1;
  z-index: 1;
}

.photo-wrapper.preload {
  z-index: 0;
}

.photo-bg {
  position: absolute;
  top: -5%;       /* Extend beyond bounds to cover blur edge fade */
  left: -5%;
  width: 110%;
  height: 110%;
  background-size: cover;
  background-position: center;
  filter: blur(30px) brightness(0.7);
  transform: scale(1.1);  /* Extra scale to cover blur edge softening */
  z-index: 0;
}

.photo-wrapper .photo {
  position: relative;
  z-index: 1;
  /* Inherits object-fit from existing styles */
}
```

#### JS Integration Changes

`createPhotoElement()` must change its return type:

```
Current:  Returns <img> element
Proposed: Returns <div class="photo-wrapper"> containing <div class="photo-bg"> and <img class="photo">
```

This affects:
- `showSinglePhoto()` -- operates on wrapper instead of img
- `showDualPortraits()` -- two wrappers side-by-side
- `loadPhoto()` -- portrait detection uses `img.naturalHeight/naturalWidth`, must access the inner `<img>`
- Cleanup code -- selects `.photo-wrapper:not(.active)` instead of `.photo:not(.active)`
- Blob URL revocation -- must revoke from inner `<img>` src AND from background-image URL

**Important: Same blob URL for both.** The background div uses the same blob URL as the img. Creating the blob URL once from the fetch response and using it for both the `img.src` and the background-image `url()` is correct -- blob URLs can be referenced multiple times. Call `URL.revokeObjectURL()` once during cleanup.

#### Conditional Application

When blurred background is disabled, the function can return bare `<img>` elements as before (no wrapper). This avoids unnecessary DOM complexity when the effect is off.

```javascript
function createPhotoContainer(img, blobUrl) {
  if (!blurredBgEnabled) {
    return img;  // Return bare img, existing code path
  }

  const wrapper = document.createElement('div');
  wrapper.className = 'photo-wrapper preload';

  const bg = document.createElement('div');
  bg.className = 'photo-bg';
  bg.style.backgroundImage = `url(${blobUrl})`;

  wrapper.appendChild(bg);
  wrapper.appendChild(img);
  return wrapper;
}
```

#### Interaction with Ken Burns

When both Ken Burns and blurred background are enabled:
- Ken Burns animation applies to the `<img>` inside the wrapper
- The blurred background div could optionally also animate (slower, inverse direction) for extra parallax depth
- OR the background could remain static (simpler, still looks good)

**Recommendation:** Apply Ken Burns only to the inner `<img>`. The blurred background stays static. This is simpler, avoids GPU memory doubling, and the visual effect is nearly identical since the background is heavily blurred anyway.

#### Memory Considerations for 24/7 Operation

- The blurred background `<div>` with `filter: blur()` creates a GPU layer. With a 30px blur radius on a fullscreen element, this uses roughly the same memory as the photo itself (~8-16MB).
- Total per-transition: ~32MB GPU (background + photo + old photo fading out)
- With proper cleanup after 1.5s, only one photo+background pair persists
- The existing blob URL revocation pattern handles memory -- no new leak vector

#### Config Integration

- New config key: `blurredBackground: false` (default off)
- Settings toggle: "Blurred Background" under Visual Effects section
- Makes most sense combined with `displayMode: 'contain'` (where black bars are visible)
- In `cover` mode, the blurred background is rarely visible (photo already fills screen), but having it enabled is harmless

## Feature 3: Date/Time Overlays

### What It Is

Two overlay elements on the slideshow:
1. **Photo date:** Shows when the displayed photo was taken (from metadata)
2. **Clock:** Shows current time (updates every minute)

Both should be toggleable independently and positioned to not obscure the photo content.

### Integration Architecture

**Approach: Fixed-position HTML elements in the slideshow page, outside `#slideshow`, updated on each photo transition (date) or on interval (clock).**

These are NOT per-photo elements. They are persistent overlays like the existing `#onThisDayIndicator` and `#controls`.

#### New DOM Elements

```html
<!-- Photo date overlay (updated per transition) -->
<div id="photoDateOverlay" class="slideshow-overlay">
  <span id="photoDate"></span>
</div>

<!-- Clock overlay (updated every minute) -->
<div id="clockOverlay" class="slideshow-overlay">
  <span id="clockTime"></span>
</div>
```

#### CSS Layer

```css
.slideshow-overlay {
  position: fixed;
  z-index: 30;  /* Above photos (z:1), below controls (z:100) */
  font-family: 'Inter', sans-serif;
  color: rgba(255, 255, 255, 0.85);
  text-shadow: 0 1px 4px rgba(0, 0, 0, 0.6);
  pointer-events: none;
  transition: opacity 0.5s;
  opacity: 0;
}

.slideshow-overlay.visible {
  opacity: 1;
}

#photoDateOverlay {
  bottom: 2rem;
  left: 2rem;
  font-size: 0.875rem;
  font-weight: 400;
}

#clockOverlay {
  bottom: 2rem;
  right: 2rem;
  font-size: 1.5rem;
  font-weight: 300;
  letter-spacing: 0.02em;
}
```

#### Position Conflict with Existing Overlays

Current fixed-position elements on the slideshow:
- `#onThisDayIndicator` -- top: 1rem, left: 1rem (z-index: 50)
- `#controls` -- bottom: 2rem, right: 2rem (z-index: 100)
- `#info` -- bottom: 2rem, left: 2rem (z-index: 100)
- `#intervalControls` -- top: 2rem, center (z-index: 100)
- `#displayModeControls` -- top: 2rem, right: 2rem (z-index: 100)
- `#keyboardHelp` -- top: 2rem, left: 2rem (z-index: 100)

**Conflict:** `#info` is already at bottom-left (same position as proposed photo date). And `#controls` is at bottom-right (same as proposed clock).

**Resolution options:**
1. **Replace `#info` with photo date** -- the info panel shows "Photo X of Y" which is less useful than the actual photo date. Could merge: show "Jan 15, 2019 -- Photo 42 of 137"
2. **Stack vertically** -- move photo date to bottom-left above #info, clock to bottom-right above #controls
3. **Top corners** -- photo date top-left (below OTD indicator when visible), clock top-right

**Recommendation:** Place overlays at top of screen. Photo date at top-left (shifts down when OTD indicator is visible). Clock at top-right. This avoids all conflicts with bottom-positioned controls and info panel.

Revised positions:
```css
#photoDateOverlay {
  top: 1rem;
  left: 1rem;
  /* When OTD indicator visible, shift down to avoid overlap */
}

#clockOverlay {
  top: 1rem;
  right: 1rem;
}
```

The overlays would have z-index: 30 (above photos at z:1, below controls at z:100). When controls appear on tap/hover, they overlay naturally at higher z-index.

#### JS Integration

**Photo date update -- in `showSinglePhoto()` and `showDualPortraits()`:**

The photo's creation date is already available. `createPhotoElement()` stores it as `img.dataset.createTime`. After transitioning to the new photo:

```javascript
if (photoDateEnabled) {
  const createTime = img.dataset.createTime;
  if (createTime) {
    const d = new Date(createTime);
    document.getElementById('photoDate').textContent =
      d.toLocaleDateString('en-US', { month: 'long', day: 'numeric', year: 'numeric' });
    document.getElementById('photoDateOverlay').classList.add('visible');
  } else {
    document.getElementById('photoDateOverlay').classList.remove('visible');
  }
}
```

**Clock update -- independent interval:**

```javascript
let clockInterval = null;

function startClock() {
  updateClock();
  clockInterval = setInterval(updateClock, 60000); // Update every minute
}

function updateClock() {
  const now = new Date();
  document.getElementById('clockTime').textContent =
    now.toLocaleTimeString('en-US', { hour: 'numeric', minute: '2-digit' });
  document.getElementById('clockOverlay').classList.add('visible');
}
```

#### Interaction with OTD Indicator

When both On This Day and photo date overlay are enabled, they both want top-left space. Solutions:
- When OTD indicator is visible, the photo date could be redundant (OTD already shows the date)
- Hide photo date when OTD indicator is showing
- OR position photo date below OTD indicator with `top: 3.5rem` when OTD is active

**Recommendation:** When OTD indicator is visible, hide photo date overlay (the date info is already in the OTD indicator). When OTD is not active, show photo date normally at top-left.

#### Config Integration

- New config keys: `showPhotoDate: false`, `showClock: false` (defaults off)
- Settings toggles under "Overlays" section
- Clock cleanup: `clearInterval(clockInterval)` on `exitSlideshow()`

## Feature 4: Stripe Donate Button

### What It Is

Replace the placeholder PayPal donation link in the index.html feedback modal with a working Stripe Checkout integration using the existing Moonacle Stripe account.

### Integration Architecture

**Approach: Stripe Checkout Session (server-side) with redirect to Stripe-hosted payment page.**

This is the simplest Stripe integration pattern. No Stripe.js embed, no custom payment form, no PCI compliance concerns.

#### Flow

```
User clicks "Support Us" in feedback modal
  -> Frontend calls POST /api/donate/create-session
  -> Backend creates Stripe Checkout Session with:
     - mode: 'payment'
     - line_items: [{ price: 'price_xxx', quantity: 1 }]
       OR
     - line_items: [{ price_data: { currency: 'usd', unit_amount: 500, product_data: { name: 'Support Okno' } }, quantity: 1 }]
     - success_url: https://okno.moonacle.com/?donation=success
     - cancel_url: https://okno.moonacle.com/?donation=cancelled
  -> Backend returns { url: session.url }
  -> Frontend redirects: window.location.href = url
  -> User completes payment on Stripe's hosted page
  -> Stripe redirects to success_url
  -> Frontend detects ?donation=success in URL params, shows thank-you message
```

#### Backend: New Route File `donate.js`

```
POST /api/donate/create-session
  - Creates Stripe Checkout Session
  - Returns { url: string }
  - No auth required (anyone can donate)
```

New dependency: `stripe` npm package.

#### Backend Changes Required

1. **New file: `donate.js`** -- Express router with single POST route
2. **Mount in `server.js`:** `app.use('/api/donate', require('./donate'))`
3. **New env vars:**
   - `STRIPE_SECRET_KEY` -- Stripe secret key (sk_live_...)
   - `STRIPE_PRICE_ID` -- Optional: pre-created Price object ID
4. **CSP update in `server.js`:** Add `https://checkout.stripe.com` to `connect-src` and `frame-src` (if using embedded checkout; not needed for redirect mode)

#### Frontend Changes

In `index.html`, the donation section of the feedback modal currently has:

```html
<a href="https://www.paypal.com/donate/?business=YOUR_PAYPAL&item_name=Okno+Development" ...>
  <button>Donate via PayPal</button>
</a>
```

Replace with:

```html
<button onclick="startDonation()">Support with Stripe</button>
```

```javascript
async function startDonation() {
  try {
    const res = await fetch('/api/donate/create-session', { method: 'POST' });
    const data = await res.json();
    if (data.url) {
      window.location.href = data.url;
    }
  } catch (error) {
    alert('Unable to start donation: ' + error.message);
  }
}
```

And on page load, check for donation result:

```javascript
const donationResult = new URLSearchParams(window.location.search).get('donation');
if (donationResult === 'success') {
  // Show thank-you toast or modal
}
```

#### Webhook (Optional, Recommended for Production)

A Stripe webhook (`POST /api/donate/webhook`) could receive `checkout.session.completed` events for:
- Logging successful donations
- Sending thank-you emails
- Tracking donation totals

For a portfolio project, this is optional. The redirect flow alone provides the user-facing experience. Webhooks add production robustness.

If implemented:
- Stripe sends POST to `/api/donate/webhook` with raw body
- Must use `express.raw()` middleware on that route (NOT `express.json()`)
- Verify webhook signature using `STRIPE_WEBHOOK_SECRET`

#### Amount Handling

Two options:
1. **Fixed amount:** Preset donation amount (e.g., $5, $10) -- simpler
2. **Customer-chooses amount:** Use Stripe Checkout `custom_amount` or multiple line items

**Recommendation:** Start with 2-3 preset amounts ($5, $10, $25) as separate buttons in the modal. Each calls `/api/donate/create-session` with a different amount parameter. This is simpler than custom amount and provides clear CTAs.

#### No Database Needed

Stripe manages all payment records. For a single-tenant portfolio app, there is no need to store donation records locally. Stripe Dashboard provides full transaction history.

## Feature 5: Demo Mode

### What It Is

Allow the app to run without Google OAuth authentication, serving a set of sample photos bundled with the application. This enables:
- Interviewer/visitor walkthroughs without requiring Google auth
- Portfolio showcase without exposing personal photos
- Development/testing without API credentials

### Integration Architecture

**Approach: Server-side demo mode flag that provides an alternative photo source when auth is not available.**

#### Activation

Environment variable: `DEMO_MODE=true`

OR auto-detect: If no `tokens.json` exists and `DEMO_MODE` is not explicitly `false`, automatically enter demo mode.

**Recommendation:** Explicit opt-in via `DEMO_MODE=true` env var. Auto-detection is fragile (user might just not have authenticated yet). Explicit is clearer.

#### Data Flow

```
Normal mode:
  /api/photo/random -> photo-cache.js -> Google Photos API (via proxy)

Demo mode:
  /api/photo/random -> demo-photos.js -> local sample photos (from /public/demo/ or /demo/)
```

#### Backend Architecture: Demo Photo Source

**Option A: Static files in `/public/demo/`**

```
/public/demo/
  photo-1.jpg
  photo-2.jpg
  ...
  photo-10.jpg
  manifest.json   -- metadata (createTime, dimensions for portrait detection)
```

The `/api/photo/random` route checks if demo mode is active. If so, instead of proxying from Google, it serves a random file from the demo directory.

**Option B: Demo-specific cache preload**

Populate `photo-cache.js` with demo entries that point to local files instead of Google baseUrls. The photo-proxy route then serves local files instead of fetching from Google.

**Recommendation: Option A** -- separate code path is cleaner than polluting the real cache with demo data. The demo photo source is architecturally distinct from the Google Photos source.

#### Implementation Detail

**New file: `demo-photos.js`**

function getRandomDemo() { ... }
function getRandomPortraitDemo() { ... }
function getDemoCount() { ... }

**Changes to `photo-proxy.js`:**

```javascript
const isDemoMode = process.env.DEMO_MODE === 'true';
const demoPhotos = isDemoMode ? require('./demo-photos') : null;

router.get('/random', async (req, res) => {
  if (isDemoMode) {
    return serveDemoPhoto(req, res);

async function serveDemoPhoto(req, res) {
  const photo = demoPhotos.getRandomDemo();
  const filePath = path.join(__dirname, 'public', 'demo', photo.file);

  res.set('Content-Type', 'image/jpeg');
  res.set('X-Photo-Id', photo.id);
  res.set('X-Photo-CreateTime', photo.createTime);
  res.set('X-Photo-IsPortrait', String(photo.height > photo.width));

  res.sendFile(filePath);
}
```

**Changes to `auth.js` / auth flow:**

The index.html currently checks `/auth/status` and shows "Sign in with Google" if not authenticated. In demo mode:
- `/auth/status` should return `{ authenticated: true, demoMode: true }` (or the frontend should skip the auth check entirely)
- The "Sign in with Google" button should be hidden
- The "Select Photos" button should be hidden
- A "Demo Mode" badge should be visible

**Implementation:** In `server.js` or `auth.js`, when `DEMO_MODE=true`:

```javascript
// Override auth status in demo mode
if (process.env.DEMO_MODE === 'true') {
  app.get('/auth/status', (req, res) => {
    res.json({ authenticated: true, demoMode: true });
  });
}
```

Note: This must be mounted BEFORE the `/auth` router to override the route. Alternatively, modify the auth router's `/status` handler to check for demo mode.

**Changes to `health.js`:**

```javascript
if (process.env.DEMO_MODE === 'true') {
  // Return demo photo count instead of cache count
  const demoPhotos = require('./demo-photos');
  return res.json({
    status: 'ok',
    demoMode: true,

      totalItems: demoPhotos.getDemoCount(),

      // ...

}
```

#### Frontend Changes for Demo Mode

In `index.html`, when `/auth/status` returns `demoMode: true`:
- Show "Demo Mode" badge
- Show "Start Slideshow" button (no picker flow)
- Hide "Sign in with Google" and "Select Photos"
- Optionally show a banner: "This is demo mode with sample photos. Sign in with Google for your own photos."

In `slideshow.html`, no changes needed -- it already fetches from `/api/photo/random` which handles both modes.

#### Demo Photo Selection

Include 8-12 high-quality, royalty-free photos with variety:
- Mix of landscape and portrait orientations (for portrait pair demo)
- Mix of dates across different years (for On This Day demo potential)
- Diverse subjects (nature, architecture, people, etc.)
- Resolution: at least 2048x1536 for iPad Pro quality
- Total size: ~30-50MB (acceptable for a repo; could .gitignore and download separately if too large)

## Suggested Build Order

Based on dependency analysis and risk assessment:

### Phase 1: Bug Fixes (No Architectural Changes)

Fix existing bugs first. These are isolated changes with no architectural impact:

1. **Picker merge (BUG-2):** Change `photo-cache.js:69` from `cache.mediaItems = items` to merge-by-id
2. **OTD fallback visibility (BUG-3):** CSS fix for black screen on fallback message
3. **502 resilience (BUG-5):** Enhanced error handling in photo-proxy.js
4. **Calendar indicator (BUG-4):** Fix conditional display logic
5. **Dual mode letterboxing (BUG-6):** CSS adjustment for landscape in dual mode

**Rationale:** Clean foundation before adding features. Bugs might interact with new code if not fixed first.

### Phase 2: Visual Effects (Frontend Only, No Backend Changes)

All CSS/JS changes in `slideshow.html` and `settings.html`:

1. **Ken Burns** -- lowest risk, additive CSS animation, zero DOM restructuring
2. **Date/time overlays** -- simple fixed-position elements, independent of photo lifecycle
3. **Blurred background** -- highest risk of the visual features due to DOM restructuring (wrapper pattern)

**Build Ken Burns first** because it validates the per-photo animation pattern without changing DOM structure. Then overlays (simple). Then blurred background (DOM restructure).

**Why blurred background is last in this phase:** It changes `createPhotoElement()` return type from `<img>` to `<div>`. This affects every downstream consumer: `showSinglePhoto()`, `showDualPortraits()`, `loadPhoto()` (portrait detection), cleanup code. Test thoroughly before proceeding.

### Phase 3: Config Integration

Wire all new features into the config system:

1. Add new keys to `config.js` defaults
2. Add new toggle sections to `settings.html`
3. Wire `loadAppConfig()` in `slideshow.html` to read new keys

**Rationale:** Separate config wiring from implementation. Features can be tested with hardcoded `true` values first, then made toggleable.

### Phase 4: Demo Mode (Backend + Frontend)

1. Create `demo-photos.js` module
2. Add demo photo files to `/public/demo/`
3. Modify `photo-proxy.js` to check `DEMO_MODE` env var
4. Modify `auth.js` / `server.js` for demo auth bypass
5. Modify `health.js` for demo photo counts
6. Modify `index.html` for demo mode UI

**Rationale:** After visual effects are done (Phase 2-3), demo mode can showcase them. Demo mode is also useful for portfolio presentation -- having working visual effects makes the demo more impressive.

### Phase 5: Stripe Integration (Backend + Frontend)

1. `npm install stripe`
2. Create `donate.js` Express router
3. Mount in `server.js`
4. Add env vars for Stripe keys
5. Update donation section in `index.html` feedback modal
6. Update CSP if needed
7. (Optional) Add webhook handler

**Rationale:** Stripe is completely independent of all other features. It touches only `index.html` (donation button) and adds a new backend route. Zero interaction with slideshow code. Can be done at any point, placed last because it's lowest priority for the portfolio showcase.

## Memory Leak Prevention Checklist (24/7 Operation)

Every v1.1 feature must maintain the existing leak-prevention discipline:

1. **Blob URLs:** Every `URL.createObjectURL()` must have a matching `URL.revokeObjectURL()` in cleanup
2. **DOM elements:** Every appended element must be removed after transition
3. **Event listeners:** No per-photo event listeners (all listeners are on fixed elements)
4. **CSS animations:** Removed with element -- no orphaned keyframe references
5. **Intervals:** `clockInterval` must be cleaned up on `exitSlideshow()`
6. **GPU layers:** `will-change: transform` elements destroyed with DOM removal -- compositor releases memory

**Testing protocol:** Run DevTools Memory panel for 30+ minutes, take heap snapshots every 5 minutes, verify flat heap profile.
