## New Stack Additions for v2.0

### 1. Database: better-sqlite3

**Recommendation:** `better-sqlite3` v12.6.2 -- synchronous SQLite driver for Node.js.

**Why SQLite over PostgreSQL:**

This is the most consequential decision in v2.0. For Okno's specific workload, SQLite is the correct choice:

| Factor | SQLite | PostgreSQL |
|--------|--------|------------|
| Write concurrency | Single writer (WAL mode) | MVCC row-level locking |
| Okno's write pattern | Infrequent: token refresh (~1/hr/user), cache updates (~1/hr/user), settings changes (rare) | Same but overengineered |
| Read concurrency | Unlimited concurrent reads (WAL mode) | Same |
| Ops overhead | Zero -- single file, no daemon | Requires postgres daemon, pg_hba.conf, users, backups |
| Deployment | Already on VPS, nothing to install | Requires `apt install postgresql`, service management |
| Backup | `cp okno.db okno.db.bak` | `pg_dump`, cron job, rotation |
| Target scale | 5-500 users | 500-100,000+ users |
| Migration path | If outgrown, migrate to Postgres later | N/A |

**The decisive argument:** Okno's write workload is extremely low. Each user writes:
- Token refresh: ~1 write/hour (automated)
- Photo cache update: 1 write when photos are selected (rare event)
- Settings change: ~1 write/month
- BaseUrl refresh: 1 write/50 min (but only updating in-memory, cache saves are batched)

At 500 concurrent users, that is roughly 500 writes/hour = ~8 writes/minute. SQLite in WAL mode handles thousands of writes per second. There is no concurrency bottleneck for this workload.

**Why better-sqlite3 over node:sqlite (built-in) or sqlite3 (async):**

| Library | API Style | Performance | Maturity |
|---------|-----------|-------------|----------|
| **better-sqlite3** | Synchronous | Fastest | 8+ years, 43M+ downloads |
| sqlite3 (npm) | Async/callback | Slower (thread pool overhead) | Older, more complex API |
| node:sqlite (built-in) | Experimental in Node 22 | Comparable | Experimental, API may change |

better-sqlite3's synchronous API is ideal for Express middleware (no async overhead for simple queries). Transactions are trivially correct: `db.transaction(() => { ... })()`.

**WAL mode configuration (required):**

```javascript
const Database = require('better-sqlite3');
const db = new Database('./data/okno.db');

// Critical performance settings
db.pragma('journal_mode = WAL');        // Concurrent reads + writes
db.pragma('busy_timeout = 5000');       // Wait up to 5s for locks
db.pragma('foreign_keys = ON');         // Enforce referential integrity
db.pragma('synchronous = NORMAL');      // Good durability/performance balance
```

**Version:** 12.6.2 (published January 2026, supports Node.js 20.x and 22.x LTS)
**Confidence:** HIGH -- verified via npm, GitHub releases, and multiple benchmarks.

**Sources:**
- [better-sqlite3 on npm](https://www.npmjs.com/package/better-sqlite3)
- [better-sqlite3 GitHub](https://github.com/WiseLibs/better-sqlite3)
- [SQLite WAL mode documentation](https://sqlite.org/wal.html)

### 2. Session Store: better-sqlite3-session-store

**Recommendation:** `better-sqlite3-session-store` v0.1.0 -- replaces `session-file-store` with SQLite-backed sessions using the same `better-sqlite3` database connection.

**Why replace session-file-store:**
- session-file-store creates one file per session in `./sessions/` directory
- With multi-user, this means many session files accumulating on disk
- SQLite session store uses the same database file as all other data -- single source of truth
- Atomic cleanup of expired sessions (SQL `DELETE WHERE expires < now`)
- Shares the same `better-sqlite3` connection (no separate database file)

**Integration with existing express-session:**

The project already uses `express-session` with `session-file-store`. The swap is minimal:

```javascript
// BEFORE (current):
const FileStore = require('session-file-store')(session);
app.use(session({
  store: new FileStore({ path: './sessions', ttl: 86400 * 365 }),
  // ...
}));

// AFTER (v2.0):
const SqliteStore = require('better-sqlite3-session-store')(session);
app.use(session({
  store: new SqliteStore({
    client: db,       // Same better-sqlite3 instance used for app data
    expired: {
      clear: true,
      intervalMs: 900000  // Clean expired sessions every 15 min
    }
  }),
  // ... rest unchanged
}));
```

**Why NOT JWT for sessions:**

| Factor | Cookie/Session (current approach) | JWT |
|--------|----------------------------------|-----|
| Instant logout | Yes (delete session from DB) | No (token valid until expiry) |
| Server storage | Small (session ID + user ref) | None |
| Complexity | Low (express-session already works) | Higher (token refresh, blacklisting) |
| Security | Simple, battle-tested | Must handle token theft, rotation, storage |
| This project | Already uses express-session | Would require rewriting auth flow |

The project already uses cookie-based sessions with express-session. Changing to JWT would be a rewrite with no benefit for a single-server app with 5-500 users. Keep what works.

**Why NOT @bttger/better-sqlite3-session-store (the scoped fork):**

While the scoped fork (@bttger/better-sqlite3-session-store v1.0.0) was published more recently, the original package (v0.1.0) has more weekly downloads (367 vs unknown), the API is stable and minimal, and session stores don't need frequent updates. The original package is sufficient.

**Alternative if session store packages prove problematic:** Write a custom store in ~50 lines. The express-session `Store` class requires only `get(sid, cb)`, `set(sid, session, cb)`, and `destroy(sid, cb)`. With better-sqlite3's synchronous API, this is trivial:

```javascript
class SqliteSessionStore extends session.Store {
  constructor(db) {
    super();
    this.db = db;
    db.exec(`CREATE TABLE IF NOT EXISTS sessions (
      sid TEXT PRIMARY KEY,
      sess TEXT NOT NULL,
      expired INTEGER NOT NULL
    )`);
  }
  get(sid, cb) {
    const row = this.db.prepare('SELECT sess FROM sessions WHERE sid = ? AND expired > ?')
      .get(sid, Date.now());
    cb(null, row ? JSON.parse(row.sess) : null);
  }
  set(sid, sess, cb) {
    const maxAge = sess.cookie?.maxAge || 86400000;
    this.db.prepare('REPLACE INTO sessions (sid, sess, expired) VALUES (?, ?, ?)')
      .run(sid, JSON.stringify(sess), Date.now() + maxAge);
    cb(null);
  }
  destroy(sid, cb) {
    this.db.prepare('DELETE FROM sessions WHERE sid = ?').run(sid);
    cb(null);
  }
}
```

This fallback is ~30 lines and eliminates a dependency entirely. Recommend starting with the package, falling back to hand-rolled if issues arise.

**Confidence:** MEDIUM -- the package works but has not been updated in 4 years. The hand-rolled fallback is HIGH confidence since express-session's Store API is well-documented and stable.

**Sources:**
- [better-sqlite3-session-store on npm](https://www.npmjs.com/package/better-sqlite3-session-store)
- [express-session Store implementation](https://www.npmjs.com/package/express-session)

### 3. Schema Migration: Hand-Rolled with PRAGMA user_version

**Recommendation:** No migration library. Use SQLite's built-in `PRAGMA user_version` for schema versioning with a hand-rolled migration runner.

**Why NOT a migration library:**
- The database has ~5 tables (users, tokens, photo_cache, settings, invite_codes)
- Schema changes will be infrequent after initial creation
- A migration library adds complexity, a CLI tool, configuration files, and a dependency -- all for a schema that barely changes
- SQLite's `PRAGMA user_version` is purpose-built for this: it stores an integer version number in the database file header
- A 20-line migration runner is simpler and more transparent than any library

**Implementation pattern:**

```javascript
// db/migrate.js
function migrate(db) {
  const version = db.pragma('user_version', { simple: true });

  if (version < 1) {
    db.exec(`
      CREATE TABLE users (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        google_id TEXT UNIQUE NOT NULL,
        email TEXT NOT NULL,
        display_name TEXT,
        created_at TEXT DEFAULT (datetime('now')),
        last_login TEXT
      );
      CREATE TABLE invite_codes (
        code TEXT PRIMARY KEY,
        created_by INTEGER REFERENCES users(id),
        used_by INTEGER REFERENCES users(id),
        created_at TEXT DEFAULT (datetime('now')),
        used_at TEXT,
        max_uses INTEGER DEFAULT 1,
        use_count INTEGER DEFAULT 0
      );
      PRAGMA user_version = 1;
    `);
  }

  if (version < 2) {
    db.exec(`
      CREATE TABLE tokens (
        user_id INTEGER PRIMARY KEY REFERENCES users(id),
        access_token TEXT NOT NULL,
        refresh_token TEXT NOT NULL,
        expiry_date INTEGER,
        scope TEXT,
        updated_at TEXT DEFAULT (datetime('now'))
      );
      CREATE TABLE photo_cache (
        id INTEGER PRIMARY KEY AUTOINCREMENT,
        user_id INTEGER NOT NULL REFERENCES users(id),
        session_id TEXT,
        media_item_id TEXT NOT NULL,
        media_item_data TEXT NOT NULL,
        created_at TEXT DEFAULT (datetime('now')),
        UNIQUE(user_id, media_item_id)
      );
      CREATE TABLE user_settings (
        user_id INTEGER PRIMARY KEY REFERENCES users(id),
        settings TEXT NOT NULL DEFAULT '{}',
        updated_at TEXT DEFAULT (datetime('now'))
      );
      PRAGMA user_version = 2;
    `);
  }

  // Future migrations: if (version < 3) { ... }
}
```

**Migration file structure:**

```
db/
  database.js      -- Opens DB, runs migrations, exports connection
  migrate.js       -- Migration definitions (version 1, 2, 3...)
  seed.js          -- Import existing JSON data as first user
```

**Why this is better than umzug/db-migrate/knex migrations:**
- Zero dependencies
- No CLI tool to learn
- No migration file naming conventions
- No migration state table (user_version is in the SQLite header)
- Migrations run automatically on server startup
- The entire migration history is in one readable file
- Rollbacks are unnecessary at this scale (just fix forward)

**Confidence:** HIGH -- `PRAGMA user_version` is a core SQLite feature documented on sqlite.org. The pattern is widely used and recommended by SQLite documentation.

**Sources:**
- [SQLite DB Migrations with PRAGMA user_version](https://levlaz.org/sqlite-db-migrations-with-pragma-user_version/)
- [SQLite's user_version pragma for schema versioning](https://gluer.org/blog/sqlites-user_version-pragma-for-schema-versioning/)

### 4. Thumbnail Generation: sharp (move to production dependency)

**Recommendation:** Move `sharp` from `devDependencies` to `dependencies`. No version change needed (^0.34.5).

**Current state:** sharp is already in the project's `devDependencies` (used by `scripts/optimize-demo-photos.js` and `scripts/generate-icons.js`). For v2.0's photo management grid, sharp will be needed at runtime to generate thumbnails.

**Why server-side thumbnail generation (not client-side):**

| Approach | Pros | Cons |
|----------|------|------|
| **Server-side (sharp)** | Cached once, served fast; works on all browsers; consistent quality | CPU cost on first generation; disk storage for thumbnails |
| **Client-side (canvas)** | No server CPU; no storage | Must regenerate every page load; varies by browser; slow on iPad |
| **Google Photos baseUrl params** | Zero processing; Google serves the size you want | baseUrls expire every 60 min; grid would show broken images after expiry |

**The decisive argument:** Google Photos baseUrl parameters (like `=w200-h200`) already support thumbnail sizing, but baseUrls expire every 60 minutes. A photo management grid showing 100+ thumbnails cannot rely on expiring URLs -- the user would see broken images if they leave the grid open. Server-generated thumbnails cached on disk are the only reliable approach.

**Thumbnail strategy:**

```javascript
const sharp = require('sharp');
const path = require('path');
const fs = require('fs');

const THUMB_DIR = './data/thumbnails';
const THUMB_SIZE = 300; // px, square crop

async function generateThumbnail(userId, mediaItemId, imageBuffer) {
  const thumbPath = path.join(THUMB_DIR, String(userId), `${mediaItemId}.webp`);

  // Skip if already generated
  if (fs.existsSync(thumbPath)) return thumbPath;

  // Ensure user thumbnail directory exists
  fs.mkdirSync(path.dirname(thumbPath), { recursive: true });

  await sharp(imageBuffer)
    .resize(THUMB_SIZE, THUMB_SIZE, {
      fit: 'cover',
      position: 'centre'
    })
    .webp({ quality: 75 })
    .toFile(thumbPath);

  return thumbPath;
}
```

**Key decisions:**
- **WebP format:** ~30% smaller than JPEG at equivalent quality. All target browsers support it (iOS Safari 14+).
- **300px square crop:** Good balance of quality and file size (~10-20KB per thumbnail). Grid displays don't need full resolution.
- **Per-user directory isolation:** `./data/thumbnails/{userId}/{mediaItemId}.webp` -- clean separation, easy to delete when user is removed.
- **Generate on first access or background job:** Don't generate thumbnails during photo selection (slows down the picker flow). Generate lazily when the grid page is first opened, or via a background queue after selection.
- **Disk cost:** 500 photos x 15KB/thumb = ~7.5MB per user. At 500 users = ~3.75GB. Acceptable for a VPS with typical 25-50GB storage.

**Version:** 0.34.5 (already in project, current as of October 2025)
**Confidence:** HIGH -- sharp is the most widely used image processing library for Node.js, already proven in this project's build scripts.

**Sources:**
- [sharp on npm](https://www.npmjs.com/package/sharp)
- [sharp documentation](https://sharp.pixelplumbing.com/)

### 5. Security: No New Libraries Needed

**Recommendation:** Use Node.js built-in `crypto` module for invite codes and CSRF protection. No new security libraries.

#### Invite Code Generation

Use `crypto.randomBytes()` from Node.js core:

```javascript
const crypto = require('crypto');

function generateInviteCode() {
  // 6 bytes = 12 hex chars, readable and typeable
  // Entropy: 2^48 = 281 trillion possibilities
  return crypto.randomBytes(6).toString('hex').toUpperCase();
  // Example: "A3F2C7B1E9D4"
}
```

**Why NOT a library like `nanoid` or `uuid`:**
- `crypto.randomBytes()` is built into Node.js -- zero dependencies
- Invite codes need to be human-typeable (12 hex chars is easy to read/type)
- UUID v4 is 36 characters -- too long for invite codes
- nanoid is a dependency for a one-liner

**Invite code format:** 12-character uppercase hex (e.g., `A3F2C7B1E9D4`). Easy to share verbally, in text messages, or written down. 281 trillion possible codes prevents brute-force guessing.

#### CSRF Protection

**The project already has CSRF protection for OAuth** via `crypto.randomBytes(32)` state parameter in `auth.js` (line 102). For other forms (settings, invite code redemption), the existing pattern is sufficient.

**Why NOT csrf-csrf or similar libraries:**
- The app uses same-origin fetch calls (vanilla JS `fetch()` to Express API)
- Express-session already sets `httpOnly`, `secure`, `sameSite` cookies
- helmet already sets security headers
- For same-origin API calls, the `SameSite=Lax` cookie attribute (default in modern browsers) prevents CSRF
- Adding a CSRF token library adds complexity with minimal benefit for this threat model

**What IS needed (and already exists):**
- `helmet` -- already installed, handles security headers
- `express-session` cookie with `httpOnly: true, secure: true` -- already configured
- CSRF state parameter for OAuth -- already implemented
- Rate limiting on sensitive endpoints (invite redemption, login) -- see below

#### Rate Limiting

**Recommendation:** `express-rate-limit` v8.2.1 -- the standard rate limiting middleware for Express.

The project already handles multiple users hitting the same endpoints. Rate limiting becomes important with multi-user to prevent:
- Invite code brute-force attempts
- Token refresh abuse
- Photo API quota exhaustion

```javascript
const rateLimit = require('express-rate-limit');

// General API limiter
const apiLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,  // 15 minutes
  max: 100,                    // 100 requests per window per IP
  standardHeaders: true,
  legacyHeaders: false,
});

// Strict limiter for auth endpoints
const authLimiter = rateLimit({
  windowMs: 15 * 60 * 1000,
  max: 10,                     // 10 attempts per 15 min
  message: { error: 'Too many attempts. Try again later.' }
});

app.use('/api/', apiLimiter);
app.use('/auth/', authLimiter);
app.use('/api/invite/redeem', authLimiter);
```

**Version:** 8.2.1 (published October 2025)
**Confidence:** HIGH -- express-rate-limit is the de facto rate limiting middleware for Express, used in millions of projects.

**Sources:**
- [express-rate-limit on npm](https://www.npmjs.com/package/express-rate-limit)
- [Node.js crypto.randomBytes() documentation](https://nodejs.org/api/crypto.html#cryptorandombytessize-callback)
- [csrf-csrf on npm](https://www.npmjs.com/package/csrf-csrf) (evaluated but not recommended)

### 6. ORM/Query Builder: None

**Recommendation:** Use raw SQL with better-sqlite3's prepared statements. No ORM, no query builder.

**Why NOT Knex, Sequelize, Drizzle, Prisma:**

| Tool | What It Adds | Why Not For Okno |
|------|-------------|-----------------|
| **Prisma** | Type-safe ORM, schema DSL, migration engine | Requires build step, generates client code, massive dependency tree (~40MB). Completely at odds with the project's "no build step" philosophy. |
| **Drizzle** | TypeScript-first ORM | Requires TypeScript. Project is vanilla JS. |
| **Sequelize** | Full ORM with models, associations | Heavy abstraction for ~5 tables. Adds ~15MB of dependencies. |
| **Knex** | Query builder + migration CLI | Most reasonable option, but still overkill. Adds migration CLI, config files, and abstraction over SQL that better-sqlite3 doesn't need. |

**Why raw SQL is correct here:**
- The schema has ~5 tables with simple relationships
- Queries are straightforward CRUD (no complex joins, aggregations, or subqueries)
- better-sqlite3's prepared statements are already parameterized (safe from SQL injection)
- Raw SQL is the most transparent and debuggable approach
- No abstraction layer means no abstraction bugs

**Example of the query complexity needed:**

```javascript
// This is the most complex query in the app:
const userPhotos = db.prepare(`
  SELECT media_item_id, media_item_data
  FROM photo_cache
  WHERE user_id = ?
  ORDER BY created_at DESC
  LIMIT ? OFFSET ?
`).all(userId, limit, offset);

// Simple CRUD - no ORM needed:
const user = db.prepare('SELECT * FROM users WHERE google_id = ?').get(googleId);
db.prepare('INSERT INTO users (google_id, email, display_name) VALUES (?, ?, ?)').run(gid, email, name);
```

If the project later grows to 20+ tables with complex relationships, reconsider Knex as a query builder (not full ORM). But for v2.0's 5-table schema, raw SQL is simpler, faster, and more maintainable.

**Confidence:** HIGH -- this is an architectural judgment call validated by the project's existing "no unnecessary abstraction" philosophy.

### 7. CLI Admin Tools: Node.js Scripts (No Framework)

**Recommendation:** Plain Node.js scripts in a `cli/` directory. No CLI framework (Commander, yargs, oclif).

**Why no CLI framework:**
- The admin CLI has ~5 commands: `create-invite`, `list-users`, `delete-user`, `list-invites`, `import-data`
- Each command is a single script: `node cli/create-invite.js`
- No subcommand routing, no flag parsing, no interactive prompts needed
- Adding Commander.js or yargs for 5 scripts is dependency bloat

**Implementation:**

```
cli/
  create-invite.js    -- Generate new invite code
  list-users.js       -- Show all users with stats
  delete-user.js      -- Remove user and their data
  list-invites.js     -- Show all invite codes and status
  import-data.js      -- Import existing JSON files as first user
```

**Usage:**
```bash
# On VPS:
cd /var/www/okno
node cli/create-invite.js
# Output: Invite code: A3F2C7B1E9D4

node cli/list-users.js
# Output:
# ID  Email                   Photos  Last Login
# 1   sam@example.com         423     2026-02-27
# 2   wife@example.com        156     2026-02-26

node cli/delete-user.js 2
# Output: Deleted user 2 (wife@example.com) and 156 cached photos

node cli/import-data.js --email sam@example.com
# Output: Imported 423 photos, tokens, and settings as user sam@example.com
```

Each script opens the same SQLite database, runs a query, prints output, and exits. The shared database module (`db/database.js`) ensures consistent connection setup.

**Confidence:** HIGH -- simple Node.js scripts are the most maintainable approach for 5 admin commands.

## Data Migration Strategy

**Recommendation:** A one-time `import-data.js` CLI script that reads existing JSON files and inserts them into the new SQLite database.

**Files to migrate:**

| File | Target Table | Notes |
|------|-------------|-------|
| `tokens.json` | `tokens` | Access token, refresh token, expiry |
| `cache.json` | `photo_cache` | All media items with metadata |
| `config.json` | `user_settings` | User preferences |

**Migration flow:**
1. Script prompts for the email of the existing user (the current single-user)
2. Creates a user record in `users` table
3. Reads `tokens.json` and inserts into `tokens` table
4. Reads `cache.json` and inserts each media item into `photo_cache` table
5. Reads `config.json` and inserts into `user_settings` table
6. Reports: "Imported X photos, tokens, and settings for user@email.com"

**Safety:** The old JSON files are NOT deleted. They remain as backup until the administrator manually removes them.

| Session store | better-sqlite3-session-store | connect-sqlite3 | connect-sqlite3 uses the older `sqlite3` async driver, not `better-sqlite3`. Would require a second SQLite driver dependency. |
| ORM | None (raw SQL) | Prisma | Requires build step, TypeScript, massive dependency tree. Antithetical to project philosophy. |
| ORM | None (raw SQL) | Knex | Reasonable option but adds unnecessary abstraction for 5 tables. Raw SQL with prepared statements is simpler and faster. |
| Migration tool | PRAGMA user_version (hand-rolled) | Umzug / db-migrate | Adds CLI tool, config files, migration state table. Total overkill for a 5-table schema that changes rarely. |
| Thumbnails | sharp (server-side) | Client-side canvas | Must regenerate every page load, varies by browser, slow on iPad. Server-cached thumbnails load instantly. |

| Invite codes | crypto.randomBytes (built-in) | nanoid / uuid | One-liner with built-in module. No dependency needed. |
| CLI framework | Plain Node scripts | Commander.js / yargs | 5 commands don't need a CLI framework. Each script is self-contained. |
| Admin interface | CLI scripts | Web admin dashboard | CLI is simpler, secure (no additional auth), and sufficient for 5-500 users. Dashboard deferred to future version. |

## What NOT to Use

| Technology | Why Not |
|------------|---------|
| **PostgreSQL** | Requires running a separate daemon, managing users, configuring pg_hba.conf, setting up backups with pg_dump. All for a workload that writes 8 times per minute at max capacity. SQLite is zero-ops. |
| **Prisma / Drizzle** | Both require a build step and TypeScript, which contradicts the project's "no build step, vanilla JS" constraint. |
| **Redis** | Sometimes suggested for session storage. Adds another daemon process. SQLite session storage is perfectly adequate at this scale. |
| **Passport.js** | Adds a thick abstraction layer over Express auth. The project already has a clean OAuth flow with google-auth-library. Passport adds 5+ packages and an unfamiliar "strategy" pattern for minimal benefit. |
| **bcrypt** | No passwords in the system -- all auth is via Google OAuth. Invite codes are one-time tokens, not passwords. |
| **JWT** | For sessions: adds token refresh complexity, no instant logout, no benefit over server sessions for single-server. For inter-service auth: not applicable (single server). |
| **TypeScript** | The project is vanilla JS with no build step. Adding TypeScript would require a build pipeline. Use JSDoc for type hints if desired. |
| **Docker** | The app runs directly on VPS with PM2. Docker adds an abstraction layer with no benefit for a single-app server. PM2 already handles process management. |
| **Mongoose / MongoDB** | Document databases are wrong for relational user data (users -> tokens, users -> photos, users -> settings). SQL is the natural fit. |

## Stack Patterns by Variant

### Database Access Pattern

All database access goes through a singleton module:

```javascript
// db/database.js
const Database = require('better-sqlite3');
const path = require('path');
const { migrate } = require('./migrate');

const DB_PATH = path.join(__dirname, '..', 'data', 'okno.db');
const db = new Database(DB_PATH);

// Performance settings
db.pragma('journal_mode = WAL');
db.pragma('busy_timeout = 5000');
db.pragma('foreign_keys = ON');
db.pragma('synchronous = NORMAL');

// Run migrations on startup
migrate(db);

module.exports = db;
```

Every module that needs data (`auth.js`, `photo-cache.js`, `config.js`, etc.) imports `db` from this single module. No connection pooling needed (better-sqlite3 is synchronous, single connection).

### Per-User Data Isolation Pattern

Every query includes `user_id` as a filter:

```javascript
// NEVER: db.prepare('SELECT * FROM photo_cache').all()
// ALWAYS: db.prepare('SELECT * FROM photo_cache WHERE user_id = ?').all(userId)
```

The `userId` comes from `req.session.userId`, which is set during OAuth callback after successful authentication.

### Auth Flow Changes for Multi-User

```
Current (single-user):
  OAuth callback → save tokens to tokens.json → set session.authenticated = true

v2.0 (multi-user):
  OAuth callback → check invite code → find/create user in DB →
  save tokens to DB (keyed by user_id) → set session.userId = user.id
```

### Thumbnail Generation Pattern

```
Photo selection flow (existing):
  User picks photos → Picker API returns media items → cache in DB

Thumbnail generation (new, background):
  After caching: queue thumbnail generation for each new item
  For each item: fetch full image → sharp resize → save to disk
  Grid page: serve pre-generated thumbnails from disk

Grid page request:
  GET /api/photos?page=1&limit=50
  → Query DB for user's cached photos (metadata only)
  → Return JSON with thumbnail URLs (/api/photos/{id}/thumb)
  → Frontend renders grid with <img src="/api/photos/{id}/thumb">
```
