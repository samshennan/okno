# Domain Pitfalls: v2.0 Multi-Tenant Conversion

**Domain:** Converting single-user Express/Node.js app to multi-tenant (Google Photos digital photo frame)
**Researched:** 2026-02-27
**Confidence:** HIGH for data isolation and OAuth pitfalls (verified against official Google docs and codebase analysis), MEDIUM for performance/VPS limits (estimates based on architecture analysis)

**Key context:** Okno is a ~4,500 LOC single-user app with a single `oAuth2Client` instance, single `tokens.json`, single `cache.json`, and single `config.json`. Every module imports the same shared OAuth client. The conversion to multi-tenant must isolate ALL of these per user without breaking the existing photo frame functionality. The first additional user will be the developer's wife -- data isolation failures will be immediately visible and personally embarrassing.

---

## Critical Pitfalls

Mistakes that cause data leaks between users, security breaches, or require rewrites.

### Pitfall 1: The Shared OAuth2Client Singleton -- User A Gets User B's Photos

**Severity:** CRITICAL -- this is THE defining risk of the entire v2.0 migration

**What goes wrong:**
The current codebase creates a single `OAuth2Client` instance at module load time (`auth.js:27-30`) and exports it for use by `photo-cache.js`, `photo-proxy.js`, and `picker.js`. Every module does `const { oAuth2Client } = require('./auth')`. This means:

1. When User A authenticates, their tokens are set on the shared `oAuth2Client` via `setCredentials()`.
2. When User B authenticates 5 minutes later, their tokens OVERWRITE User A's on the same shared instance.
3. When User A's slideshow fetches the next photo via `photo-proxy.js:67`, it calls `oAuth2Client.getAccessToken()` -- which now returns User B's token.
4. The proxy then fetches User A's cached photo URLs using User B's authorization. Google returns 403 (User B has no access to User A's Picker session) and the slideshow breaks.
5. Worse: if both users happened to pick overlapping photos, User A silently sees User B's private photos with no error.

**Why it happens:**
Node.js modules are cached after first `require()`. The `oAuth2Client` object is created once in `auth.js` and shared by reference across all files. This is the textbook single-tenant-to-multi-tenant failure: global state that implicitly assumes one user.

**Warning signs:**
- Second user's login causes first user's slideshow to break with 403/502 errors
- Users report seeing "wrong" photos (photos they didn't select)
- `photo-proxy.js` logs show mismatched `photoId` vs authorization context

**Prevention:**
1. **Create OAuth2Client per-request, not per-module.** Each API call must construct a fresh `OAuth2Client` and call `setCredentials()` with tokens retrieved from that specific user's DB record or session.
2. **Never store tokens on a shared object.** Store tokens in the database keyed by `userId`. When making Google API calls, load the specific user's tokens, create a temporary `OAuth2Client`, set credentials, make the call, then discard the client.
3. **Remove the `oAuth2Client` export entirely.** Replace with a factory function: `function getOAuthClientForUser(userId)` that loads user-specific tokens from DB.
4. **Add integration test:** Two users authenticate, verify each user's proxy calls use their own tokens by checking the `Authorization` header in logs.

**Recovery if it happens:**
- Immediate: Restart the server (clears in-memory state, but doesn't fix the architecture)
- Proper fix: Requires the factory function refactor -- cannot be patched, must be redesigned

**Which phase should address it:** The FIRST phase of multi-tenant work. This is prerequisite to everything else. No other multi-tenant feature works until per-user OAuth is solved.

**Confidence:** HIGH -- verified by direct codebase analysis of `auth.js`, `photo-cache.js`, `photo-proxy.js`, and `picker.js`. All four files import the shared singleton.

### Pitfall 2: The Single Global Photo Cache -- User B Overwrites User A's Photo Collection

**Severity:** CRITICAL -- one user's photo selection replaces or contaminates another's

**What goes wrong:**
`photo-cache.js` maintains a single in-memory `cache` object (`line 27-32`) with one `mediaItems` array and one `sessionId`. When User B completes the Picker flow and calls `photoCache.setItems()`, their items merge into User A's collection (or replace it if the merge logic fails). The slideshow then serves a mixed bag of both users' photos to whoever is watching.

The current merge logic (`line 70-93`) deduplicates by `item.id`, but Google Photos item IDs are unique per user's library. Two users will never have the same item IDs, so the "dedup" logic provides zero protection -- it just appends everything together.

**Why it happens:**
- `cache.json` is a single file on disk with no user context
- The in-memory `cache` object has no `userId` field
- `setItems()` takes `(items, sessionId)` but no `userId` parameter
- `getRandomItem()` returns from the combined pool with no user filtering

**Warning signs:**
- Cache size grows larger than either user's individual selection
- Slideshow shows photos neither user selected (they belong to the other user)
- `cache.json` grows continuously with each user's Picker session

**Prevention:**
1. **Database table with userId foreign key.** Media items stored in a `media_items` table with a `user_id` column. Every query includes `WHERE user_id = ?`.
2. **Per-user in-memory cache Map.** Replace the single `cache` object with `Map<userId, UserCache>`. All cache functions take `userId` as first parameter.
3. **Per-user Picker sessionId.** Each user's Picker session must be tracked separately. The current code stores one `sessionId` globally -- with multi-user, each user has their own active Picker session.
4. **Add constraint:** `UNIQUE(user_id, photo_id)` in the database to prevent cross-user contamination even if application logic has a bug.

**Recovery if it happens:**
- If caches are merged: Must re-authenticate both users and re-select photos via Picker. There's no way to un-merge photos since the cache doesn't track which user added which item.
- If using DB: Row-level isolation makes recovery trivial -- just delete rows with wrong `user_id`.

**Which phase should address it:** Same phase as Pitfall 1 (first phase). Cache isolation and OAuth isolation are two halves of the same problem.

**Confidence:** HIGH -- verified by direct analysis of `photo-cache.js` source code.

### Pitfall 3: Session Fixation on OAuth Login -- Attacker Hijacks Authenticated Session

**Severity:** CRITICAL -- enables session hijacking

**What goes wrong:**
The current `auth.js` OAuth callback (`line 122-180`) sets `req.session.authenticated = true` but does NOT call `req.session.regenerate()` after successful authentication. This means the session ID assigned to the user before login (during anonymous browsing) is the same session ID used after login. An attacker who knows or sets the pre-login session ID can hijack the authenticated session.

Attack scenario:
1. Attacker visits the app, gets session cookie `sid=ATTACKER_SESSION`
2. Attacker crafts a link: `https://okno.moonacle.com/auth/login` and tricks User A into clicking it while the attacker's session cookie is set (e.g., via subdomain cookie injection)
3. User A completes OAuth login. The session `ATTACKER_SESSION` now has `authenticated: true`
4. Attacker uses `ATTACKER_SESSION` to access User A's photos

**Why it happens:**
- express-session does NOT automatically regenerate session IDs on login
- The developer must explicitly call `req.session.regenerate()` -- this is a known gap in express-session's API
- The current code was written for single-user where session fixation is less impactful (one user = one valid session). With multi-user, session fixation becomes a real vector.

**Warning signs:**
- Security audit tools flag "session not regenerated after login"
- OWASP ZAP or similar scanner reports session fixation vulnerability

**Prevention:**
```javascript
// In auth.js callback, AFTER successful OAuth token exchange:
const userData = { authenticated: true, userId: user.id, tokens: encryptedTokens };
req.session.regenerate((err) => {
  if (err) return res.status(500).send('Session error');
  // Copy user data to new session
  Object.assign(req.session, userData);
  req.session.save((err) => {
    if (err) return res.status(500).send('Session save error');
    res.redirect('/');
  });
});
```

**Important caveat:** `req.session.regenerate()` destroys the old session and creates a new one. Any data stored in the old session (like `oauthState` for CSRF verification) must be read BEFORE calling regenerate. The CSRF state check happens on line 125 (before the `regenerate` call), so this is safe.

**Recovery if it happens:**
- Rotate the session secret (invalidates all existing sessions, forcing re-login)
- Add `regenerate()` call to the callback
- No data loss -- sessions only contain auth state, not photos

**Which phase should address it:** Authentication/session management phase.

**Confidence:** HIGH -- verified by OWASP session fixation guidance and express-session documentation. The current code does NOT call `regenerate()`.

### Pitfall 4: Refresh Token Not Persisted Per User -- Google Only Issues It Once

**Severity:** CRITICAL -- user permanently loses access if refresh token is lost

**What goes wrong:**
Google only returns a `refresh_token` on the FIRST authorization for a given user-app combination (unless `prompt=consent` is forced). The current code forces `prompt: 'consent'` (`auth.js:110`), which works around this for a single user. But with multi-user:

1. User A logs in with `prompt=consent`, gets refresh_token, saved to `tokens.json`
2. User B logs in with `prompt=consent`, gets their refresh_token, OVERWRITES `tokens.json`
3. User A's refresh_token is permanently lost
4. When User A's access_token expires (after ~1 hour), the server can't refresh it
5. User A's slideshow stops working with no recovery path except re-authenticating

Even with a proper database, if the refresh_token is not stored correctly at the moment of first authorization, it may be lost forever -- Google will not re-issue it unless the user revokes app access in their Google Account settings and re-authorizes.

**Why it happens:**
- Google's OAuth2 design: refresh_token issued only on first consent grant
- `prompt=consent` forces re-consent, which DOES return a new refresh_token, but only because it treats the authorization as "first time"
- The `saveTokens()` function (`auth.js:51-78`) has merge logic to preserve existing refresh_tokens, but it operates on a SINGLE `tokens.json` file shared by all users
- Race condition: If two users authenticate within seconds, the second `saveTokens()` call overwrites the first

**Warning signs:**
- User's slideshow works for ~1 hour then stops (access_token expires, no refresh_token to renew)
- Logs show "Token has been expired or revoked" errors
- `tokens.json` contains only the most recent user's credentials

**Prevention:**
1. **Store refresh_token in DB immediately upon OAuth callback.** The callback is the ONE moment you reliably have the refresh_token. Store it in `users.refresh_token` column before doing anything else.
2. **Keep `prompt: 'consent'` for now.** This ensures a refresh_token is always returned, at the cost of showing the consent screen every time. For a small user base (invite-only), this is acceptable UX.
3. **Add a "refresh token health check" to the health endpoint.** For each user, verify their stored refresh_token can be used to obtain an access_token. Alert if any user's refresh_token is invalid.
4. **Never overwrite a valid refresh_token with null.** Google sometimes returns token responses without a refresh_token (on subsequent auths). If `tokens.refresh_token` is undefined in the response, DO NOT update the DB column.

**Recovery if it happens:**
- User must go to https://myaccount.google.com/permissions, revoke the app, then re-authenticate with `prompt=consent`
- This is a terrible user experience and must be prevented architecturally

**Which phase should address it:** Same phase as per-user OAuth (Pitfall 1).

**Confidence:** HIGH -- verified against official Google OAuth documentation ("refresh_token is only returned on the first authorization") and google-auth-library-nodejs behavior.

### Pitfall 5: Missing sameSite Cookie Attribute -- CSRF Vulnerability in Multi-User Context

**Severity:** CRITICAL in multi-user context

**What goes wrong:**
The current session cookie configuration (`server.js:69-73`) sets `secure: true` and `httpOnly: true` but does NOT set `sameSite`. Modern browsers default to `sameSite: 'Lax'`, which provides basic CSRF protection. However, explicitly setting this is important because:

1. Some older browsers (iOS 12 Safari, older Chrome) default to `sameSite: 'None'`, which sends cookies on cross-site requests
2. Without explicit `sameSite`, the behavior is browser-dependent and untestable
3. The POST endpoints (`/auth/logout`, `/api/config`, `/api/picker/start`, `/api/picker/complete`) are vulnerable to CSRF if cookies are sent cross-site

In single-user mode, CSRF is low-impact (the attacker can only affect the one authorized user). In multi-user mode, CSRF could let an attacker trigger actions on behalf of any authenticated user.

**Warning signs:**
- Security scanner flags missing `sameSite` attribute
- Cross-origin requests unexpectedly succeed with authentication

**Prevention:**
```javascript
cookie: {
  secure: process.env.NODE_ENV === 'production',
  httpOnly: true,
  sameSite: 'lax',  // ADD THIS
  maxAge: 365 * 24 * 60 * 60 * 1000
}
```

**Which phase should address it:** Session management / security hardening phase.

**Confidence:** HIGH -- verified against OWASP CSRF Prevention Cheat Sheet and express-session documentation.

## Technical Debt Patterns

Patterns that create compound problems over time if not addressed early.

### Debt 1: File-Based Storage Race Conditions During Migration Period

**What goes wrong:**
During migration from `tokens.json`/`cache.json`/`config.json` to database, there will be a transition period where some code paths read from files and others from DB. If both are "live" simultaneously:

- `fs.writeFileSync()` is synchronous and blocks the event loop, but two concurrent requests can still interleave reads and writes (Request A reads old data, Request B writes new data, Request A writes based on stale data -- overwriting B's changes)
- `fs.readFileSync()` during a partial `writeFileSync()` can return truncated JSON, crashing the parser

**Prevention:**
- **Atomic cutover, not gradual migration.** Move ALL storage to DB in a single deployment. Don't try to keep file-based storage as a "fallback."
- **One-time migration script:** Read existing JSON files, insert into DB, then rename the JSON files to `.bak` (don't delete -- keep as rollback).
- **Remove all `fs.readFileSync`/`fs.writeFileSync` calls** from the production code path. If file I/O remains "just in case," it WILL cause confusion.

**Which phase should address it:** Database migration phase (early in v2.0).

---

### Debt 2: In-Memory Cache Without Eviction Strategy

**What goes wrong:**
The current `photo-cache.js` loads the entire cache into memory on startup (`loadCache()`, line 249). With one user and up to 2,000 photos, this is ~2-5MB of JSON. With N users, it becomes N * 2-5MB. At 20 users, that's 40-100MB of in-memory photo metadata that never gets evicted.

Additionally, the `refreshBaseUrls()` function fetches ALL items for a session and rebuilds the entire in-memory map. With multiple users, N refresh cycles running every 50 minutes will spike memory usage periodically.

**Prevention:**
- **Lazy load from DB, not eager load to memory.** Query the DB for specific user's items when needed, not all users' items at startup.
- **LRU cache for hot data.** Keep recently-accessed users' metadata in memory with an eviction policy (e.g., `lru-cache` package). Users who haven't accessed their slideshow in >1 hour get evicted from memory.
- **Cap per-user items in memory.** Even with LRU, limit to the active user's items, not all users.

**Which phase should address it:** Per-user cache isolation phase.

---

### Debt 3: Single setInterval for baseUrl Refresh Becomes N Timers

**What goes wrong:**
Currently, `photo-cache.js:91` creates ONE `setInterval` at 50-minute intervals to refresh all cached baseUrls. With multi-user, naive conversion would create one timer per user. Problems:

1. **Timer accumulation:** If User A logs in, a timer is created. If User A logs out and back in, another timer is created (the old one is never cleared because there's no cleanup path). After 10 logins, 10 timers are running.
2. **Thundering herd:** If all N users' timers fire at the same 50-minute mark, the server makes N * (numPhotos/100) API calls simultaneously, hitting Google's rate limits and spiking memory.
3. **Orphaned timers:** If a user is deleted but their timer is still running, the refresh will fail (no valid tokens) and log errors forever.

**Prevention:**
- **Single scheduler, multiple jobs.** Use one central scheduler (e.g., a single `setInterval` or a job queue) that iterates through users needing refresh. Stagger refresh times so users don't all refresh simultaneously.
- **Jitter:** Add random delay (0-5 minutes) to each user's refresh interval so they don't synchronize.
- **Only refresh active users.** If a user hasn't accessed their slideshow in >24 hours, skip their refresh. baseUrls only matter when the slideshow is actually being viewed.
- **Store timer references with cleanup.** Associate timers with user records and clear them on user deletion/logout.

**Which phase should address it:** Per-user cache and refresh phase.

## Integration Gotchas

Pitfalls specific to how this app's components interact during multi-tenant conversion.

### Gotcha 1: Google OAuth Consent Screen 100-User Lifetime Cap

**What goes wrong:**
The Okno app uses the `photospicker.mediaitems.readonly` scope, which Google classifies as sensitive. For apps in "Testing" publishing status with External user type, Google enforces a **lifetime cap of 100 unique users** who can grant consent. This cap cannot be reset or increased without completing Google's app verification process.

This means: even with a working invite code system, the 101st unique Google account that tries to authenticate will be blocked by Google (not by your code) with an "unverified app" warning screen.

**Why this is subtle:**
- During development, you'll only test with 2-3 accounts and never hit the limit
- The cap is LIFETIME (total unique users ever), not concurrent users
- Test users consume cap slots too
- The scary "This app isn't verified" warning screen will confuse family/friends before they even get to your invite code flow

**Prevention:**
1. **For initial launch (family/friends <20 users): Accept the limitation.** 100 users is plenty for invite-only.
2. **Add clear UX guidance.** When users see Google's "This app isn't verified" screen, show them instructions: "Click Advanced > Go to Okno (unsafe) to continue."
3. **Plan for verification if scaling beyond ~50 users.** Google verification requires privacy policy, terms of service, homepage, and potentially a security assessment.
4. **Consider "Internal" user type** if all users are within a Google Workspace organization. Internal apps bypass the consent screen entirely. (Not applicable if users have personal Gmail accounts.)

**Warning signs:**
- Users report being unable to log in despite valid invite codes
- Google Cloud Console shows user cap approaching limit
- New users see an error page they can't get past

**Which phase should address it:** Documentation/onboarding phase. Not a code fix -- a UX and planning concern.

**Confidence:** HIGH -- verified against Google Cloud Platform Console Help documentation on unverified apps and user caps.

### Gotcha 2: Picker API Session Limits with Multiple Users

**What goes wrong:**
The Picker API enforces limits on concurrent sessions per project (exact numbers undisclosed by Google). With multiple users each creating Picker sessions, the project could hit session limits. Unlike API request quotas (100,000/min), session limits are opaque and may be much lower.

Additionally, the current code never calls `sessions.delete` to clean up completed Picker sessions. With single-user this was harmless. With multi-user, orphaned sessions from each user accumulate and count against the limit.

**Prevention:**
1. **Delete Picker sessions after retrieving media items.** After `picker.js` completes the `/complete/:sessionId` flow and caches all items, immediately call `DELETE /v1/sessions/{sessionId}` to clean up.
2. **Track active sessions in DB.** Store `(userId, sessionId, createdAt)` so you can identify and clean up stale sessions.
3. **Add session cleanup cron.** Every hour, delete any Picker sessions older than 30 minutes (the Picker flow should complete within minutes).
4. **Handle 429 errors gracefully.** If session creation returns 429, show the user a "please try again in a few minutes" message rather than a generic error.

**Which phase should address it:** Picker integration refactor phase.

**Confidence:** MEDIUM -- Google doesn't disclose exact session limits. The cleanup recommendation is based on Google's own documentation advising proactive session management.

### Gotcha 3: The Photo Proxy Memory Spike with Concurrent Users

**What goes wrong:**
`photo-proxy.js:129` does `const arrayBuffer = await imageResponse.arrayBuffer()` followed by `Buffer.from(arrayBuffer)` for EVERY photo request. This loads the entire photo into Node.js memory before sending it to the client. A typical photo at `=w2048-h1536` is 500KB-2MB. With single-user, one photo loads at a time. With N concurrent slideshow viewers:

- 5 concurrent users = 5 photos in memory = 2.5-10MB (manageable)
- 20 concurrent users = 20 photos in memory = 10-40MB (concerning)
- 20 concurrent users during a baseUrl refresh cycle = refresh API calls + photo proxying simultaneously = memory pressure

The real danger is the event loop: `arrayBuffer()` is async but holds the full image in memory until `res.send(buffer)` completes. If the client is on a slow connection, the buffer stays in memory longer.

**Prevention:**
1. **Stream, don't buffer.** Replace `arrayBuffer()` + `Buffer.from()` with piping the response body directly:
   ```javascript
   const imageResponse = await fetch(imageUrl, { headers: { 'Authorization': `Bearer ${token}` } });
   res.set('Content-Type', imageResponse.headers.get('content-type'));
   imageResponse.body.pipe(res);
   ```
2. **Add request concurrency limit.** Use a semaphore or queue (e.g., `p-limit` package) to limit concurrent photo proxy requests to 5-10. Additional requests wait in queue rather than all loading simultaneously.
3. **Consider thumbnail proxy endpoint.** For the photo grid (new feature), serve thumbnails at `=w256-h256` instead of full-res `=w2048-h1536`. This is 50-100x less memory per request.

**Which phase should address it:** Photo proxy refactor phase (when adding photo grid).

**Confidence:** MEDIUM -- memory estimates are based on typical JPEG sizes at the specified resolutions. Exact impact depends on VPS memory allocation.

### Gotcha 4: baseUrl Refresh Uses Stale Picker Session After User Re-Authenticates

**What goes wrong:**
The current `refreshBaseUrls()` function (`photo-cache.js:186-246`) uses the stored `cache.sessionId` to re-fetch media items from Google. In multi-user, consider this scenario:

1. User A authenticates, selects photos via Picker, gets `sessionId: "abc123"`
2. User A's refresh_token expires or is revoked (e.g., user changes Google password)
3. User A re-authenticates with `prompt=consent`, gets new tokens
4. User A opens Picker again, gets NEW `sessionId: "xyz789"`
5. The old `sessionId: "abc123"` is now invalid, but if any code still references it, the refresh fails
6. Photos selected in session "abc123" can no longer have their baseUrls refreshed

**Prevention:**
1. **Track session-to-user relationship in DB.** Each Picker session belongs to a specific user and has a creation timestamp.
2. **When user creates new Picker session, mark old session as inactive.** Don't delete old photos from cache, but stop trying to refresh them via the old session.
3. **Refresh using the user's LATEST session only.** The current code already does this (`cache.sessionId` is updated on `setItems()`), but the multi-user version must do it per-user.
4. **Handle refresh failures gracefully.** If a refresh returns 404 (session expired), mark the user's cache as "needs re-selection" and show a UI prompt rather than silently serving stale baseUrls.

**Which phase should address it:** Per-user cache and refresh phase.

**Confidence:** HIGH -- verified against Picker API session documentation and current codebase behavior.

## Performance Traps

Issues that only manifest under multi-user load, not during single-user development.

### Trap 1: N Users x 50-Minute Refresh = API Quota Pressure

**What goes wrong:**
Each user's baseUrl refresh calls `GET /v1/mediaItems?sessionId=X` with pagination (100 items per page). A user with 2,000 photos = 20 API calls per refresh cycle. With N users refreshing every 50 minutes:

- 5 users x 20 calls = 100 API calls per 50-minute cycle (trivial)
- 50 users x 20 calls = 1,000 API calls per cycle (still fine, quota is 100K/min)
- 500 users x 20 calls = 10,000 API calls per cycle (fine for per-minute, but potential concern for total daily volume)

The real risk is not the quota (which is generous) but the memory and CPU cost of processing 10,000+ responses, parsing JSON, and updating the database 10,000 times in a burst.

**Prevention:**
- **Stagger refresh intervals.** Don't have all users refresh at minute 50. Spread refreshes evenly across the 50-minute window.
- **Refresh only when needed.** If a user's slideshow hasn't been accessed in the last hour, skip their refresh. baseUrls only matter when photos are being displayed.
- **Batch DB updates.** Instead of one DB write per photo per user, batch-update all of a user's baseUrls in a single transaction.

**Which phase should address it:** Per-user refresh scheduling phase.

---

### Trap 2: VPS Memory Ceiling with Multiple In-Memory Caches

**What goes wrong:**
A typical low-cost VPS has 1-2GB RAM. Node.js default heap is ~1.5GB (V8's default). Current single-user memory footprint:

- Node.js baseline: ~50MB
- Express + middleware: ~20MB
- Single user cache (2000 items): ~3-5MB
- Session file store: ~1MB
- Winston logger buffers: ~5MB
- Total: ~80MB

With multi-user (if caches are kept in memory):
- 10 users x 5MB cache = 50MB additional
- 50 users x 5MB cache = 250MB additional
- Session store growth (1 session file per user): negligible
- Total with 50 users: ~330MB

This is fine for a 2GB VPS. But the danger is periodic spikes: during baseUrl refresh, the server fetches fresh data AND holds the old data until the swap completes, briefly doubling cache memory. With 50 users refreshing in a burst, peak memory could hit 580MB+.

**Prevention:**
- **DB-first architecture.** Store caches in SQLite/PostgreSQL, not in memory. Only load the active user's data when needed.
- **Set `--max-old-space-size` explicitly.** Don't rely on V8 defaults. Set it to 75% of VPS RAM: `node --max-old-space-size=1536 server.js` for a 2GB VPS.
- **Add memory monitoring.** Log `process.memoryUsage()` to the health endpoint. Alert if RSS exceeds 70% of available RAM.
- **Use PM2 memory restart.** Configure PM2 to restart the process if memory exceeds a threshold: `max_memory_restart: '1G'` in `ecosystem.config.js`.

**Which phase should address it:** Infrastructure/deployment phase.

---

### Trap 3: Photo Grid Thumbnail Requests Multiply Server Load

**What goes wrong:**
The new photo management grid will display thumbnails of all a user's cached photos. A user with 500 photos viewing their grid = 500 thumbnail requests hitting the photo proxy simultaneously. Each request:

1. Loads user from session (DB lookup)
2. Gets user's access token (DB lookup or token refresh)
3. Fetches thumbnail from Google Photos (external HTTP request)
4. Pipes/buffers the response back to the client

With 500 concurrent requests per grid page load, the server will exhaust available sockets, connections, and memory. The slideshow loads ONE photo at a time; the grid loads ALL visible thumbnails at once.

**Prevention:**
1. **Pagination.** Never load all 500 thumbnails at once. Show 20-50 per page with "Load More" or infinite scroll.
2. **Virtual scrolling.** Only render thumbnails in the viewport. As the user scrolls, render new thumbnails and destroy off-screen ones.
3. **Use small thumbnail URLs.** Request `=w128-h128-c` (cropped square thumbnail, ~5-15KB each) instead of full-res. This reduces both Google API bandwidth and browser memory.
4. **Lazy loading with `loading="lazy"`.** Native browser lazy loading defers off-screen thumbnail fetches.
5. **Concurrency limit on proxy.** Limit concurrent Google API requests per user to 3-5. Queue additional requests.
6. **Client-side thumbnail caching.** After first load, cache thumbnail blobs in IndexedDB or Service Worker cache. The grid shouldn't re-fetch thumbnails on every page visit.

**Which phase should address it:** Photo grid implementation phase.

## Security Mistakes

Beyond session fixation (Pitfall 3), these are multi-user-specific security issues.

### Mistake 1: Invite Code Brute Force via Timing Attack

**What goes wrong:**
If invite code validation uses simple string comparison (`===`), the comparison short-circuits at the first mismatched character. An attacker can measure response times to determine how many characters of their guess are correct, reducing the search space from exponential to linear.

For a 6-character alphanumeric invite code (36^6 = ~2.2 billion combinations), brute force is impractical. But with a timing attack, the attacker only needs ~36 * 6 = 216 requests to guess the code character-by-character.

**Prevention:**
1. **Use `crypto.timingSafeEqual()` for comparison:**
   ```javascript
   const crypto = require('crypto');
   function validateInviteCode(input, stored) {
     const inputBuf = Buffer.from(input.padEnd(32), 'utf8');
     const storedBuf = Buffer.from(stored.padEnd(32), 'utf8');
     return crypto.timingSafeEqual(inputBuf, storedBuf);
   }
   ```
   Note: Pad to equal length since `timingSafeEqual` requires same-length buffers.

2. **Rate limit invite code attempts.** Max 5 attempts per IP per hour. Use `express-rate-limit` on the invite code endpoint.

3. **Use long invite codes.** 8+ characters, mixed case + digits = 62^8 = ~218 trillion combinations. Even with timing attack, this is impractical.

4. **Hash invite codes in DB.** Store `bcrypt(inviteCode)` in the database, not plaintext. Use `bcrypt.compare()` which is constant-time by design.

5. **One-time use with expiration.** Each code can be redeemed once and expires after 7 days. This limits the attack window.

**Which phase should address it:** Invite code implementation phase.

**Confidence:** HIGH -- timing attacks on string comparison are well-documented (OWASP, Node.js crypto docs).

---

### Mistake 2: Invite Code Reuse and Enumeration

**What goes wrong:**
If invite codes can be reused (not marked as "consumed" after redemption), a leaked code gives unlimited access to anyone who finds it. If invite codes follow a predictable pattern (sequential numbers, timestamps), an attacker can enumerate valid codes.

**Prevention:**
1. **Mark as consumed immediately on redemption.** DB column: `redeemed_by`, `redeemed_at`. Check these before allowing redemption.
2. **Use cryptographically random codes.** `crypto.randomBytes(6).toString('base64url')` generates an 8-character URL-safe code with 48 bits of entropy.
3. **Don't expose valid/invalid distinction.** Return the same error message ("Invalid or expired invite code") whether the code doesn't exist, is already used, or is expired. Don't let attackers distinguish between "valid but used" and "doesn't exist."
4. **Log all redemption attempts.** Track IP, timestamp, and code attempted for security auditing.

**Which phase should address it:** Invite code implementation phase.

---

### Mistake 3: User Data Leaks via API Endpoints Without Auth Middleware

**What goes wrong:**
Currently, several endpoints have NO authentication check:
- `GET /api/config` -- returns the global config (no auth required)
- `POST /api/config` -- updates the global config (no auth required)
- `GET /api/photo/random` -- serves photos (no auth required -- the slideshow needs to work without re-auth)
- `GET /api/health` -- shows system status (intentionally public)

With multi-user, these endpoints must be scoped to the authenticated user. If `/api/config` returns a shared global config, one user's settings affect everyone. If `/api/photo/random` doesn't check which user is requesting, it serves the wrong user's photos.

**Prevention:**
1. **Auth middleware on all user-data endpoints.** Every endpoint that reads or writes user-specific data must validate the session and extract `userId`:
   ```javascript
   function requireAuth(req, res, next) {
     if (!req.session?.userId) {
       return res.status(401).json({ error: 'Not authenticated' });
     }
     req.userId = req.session.userId;
     next();
   }
   ```
2. **Scope all queries by userId.** `getConfig(userId)`, `getRandomPhoto(userId)`, etc.
3. **Keep health endpoint public** (no user data) but remove any user-specific details from it.
4. **The slideshow "no re-auth" requirement:** The slideshow runs unattended on iPads. The session cookie handles auth -- the user doesn't need to re-enter credentials, but the session must exist and be valid.

**Which phase should address it:** Auth middleware phase (same as session management).

---

### Mistake 4: Storing OAuth Tokens Unencrypted in Database

**What goes wrong:**
Google OAuth tokens (especially refresh_tokens) are long-lived credentials that grant access to a user's Google Photos. If the database is compromised (SQL injection, backup stolen, VPS breached), unencrypted tokens give the attacker access to every user's Google Photos.

Currently, `tokens.json` stores tokens in plaintext -- acceptable for single-user on a private VPS, but unacceptable for multi-user.

**Prevention:**
1. **Encrypt tokens at rest.** Use AES-256-GCM with a server-side encryption key stored in environment variables:
   ```javascript
   const crypto = require('crypto');
   const ENCRYPTION_KEY = process.env.TOKEN_ENCRYPTION_KEY; // 32-byte key

   function encryptToken(token) {
     const iv = crypto.randomBytes(16);
     const cipher = crypto.createCipheriv('aes-256-gcm', Buffer.from(ENCRYPTION_KEY, 'hex'), iv);
     let encrypted = cipher.update(token, 'utf8', 'hex');
     encrypted += cipher.final('hex');
     const tag = cipher.getAuthTag().toString('hex');
     return `${iv.toString('hex')}:${tag}:${encrypted}`;
   }
   ```
2. **Separate encryption key from database.** The key should be in `.env`, not in the DB. If the DB is compromised without the key, tokens are useless.
3. **Consider scope of effort.** For a small invite-only app on a private VPS, this may be over-engineering. Evaluate based on user count and risk tolerance. At minimum, ensure the VPS has proper access controls and the DB file isn't world-readable.

**Which phase should address it:** Database design phase. Decide on encryption strategy early so the schema accounts for encrypted column sizes.

**Confidence:** MEDIUM -- encryption at rest is best practice, but for <20 users on a personal VPS, the risk vs. effort tradeoff may favor simpler approaches (file permissions, VPS security) initially.

## UX Pitfalls

Mistakes that don't break the system but frustrate users or create confusion.

### UX Pitfall 1: "This App Isn't Verified" Google Warning Scares Users Away

**What goes wrong:**
When a new user clicks "Sign in with Google," they see a full-page warning: "This app isn't verified. This app hasn't been verified yet by Google." with a small "Advanced" link. Most non-technical users will refuse to proceed. This is Google's unverified app screen for apps using sensitive scopes.

**Prevention:**
1. **Pre-educate users before they hit the Google screen.** On your login page, add a prominent message: "When Google asks, click 'Advanced' then 'Go to Okno (unsafe)'. This is normal for self-hosted apps."
2. **Include screenshots in onboarding.** Show users exactly what the warning looks like and where to click.
3. **Consider verification** if user base grows beyond family/friends. Requires privacy policy, ToS, and homepage.

**Which phase should address it:** Onboarding UX phase.

---

### UX Pitfall 2: Photo Grid Without Loading States Feels Broken

**What goes wrong:**
If the photo grid loads 50 thumbnails and each requires a proxy request to Google, the grid will appear empty for 2-5 seconds, then all thumbnails appear at once. Or worse, thumbnails load in random order, causing layout shifts as images of different aspect ratios load.

**Prevention:**
1. **Placeholder thumbnails.** Show colored rectangles or blur-hash placeholders while images load.
2. **Fixed aspect ratio containers.** Use `aspect-ratio: 1/1` (for square crops) or `aspect-ratio: 4/3` on thumbnail containers to prevent layout shift.
3. **Progressive loading indicator.** "Loading 12 of 50 photos..." with a progress bar.
4. **Skeleton screen pattern.** Show the grid layout with grey placeholder boxes immediately, then replace with actual thumbnails as they load.
5. **`loading="lazy"` on `<img>` tags.** Only load thumbnails as they scroll into view.

**Which phase should address it:** Photo grid implementation phase.

---

### UX Pitfall 3: No Feedback When Invite Code Is Invalid

**What goes wrong:**
If the invite code form silently fails or shows a generic "Error," users don't know what went wrong. Did they mistype? Is the code expired? Was it already used?

**Prevention:**
1. **Specific but safe error messages:**
   - "Invalid invite code" (for wrong code, expired code, OR already-used code -- same message for security)
   - "Invite code is required" (empty input)
2. **Visual feedback:** Shake animation on the input field for invalid codes.
3. **Show code format hint:** "Enter the 8-character code you received" so users know the expected format.
4. **Auto-focus and auto-uppercase:** The invite code input should be focused on page load and auto-uppercase input for consistency.

**Which phase should address it:** Invite code UX phase.

---

### UX Pitfall 4: User Can't Tell Whose Frame They're Looking At

**What goes wrong:**
After multi-tenant conversion, each user has their own slideshow URL (or the same URL with different sessions). If someone shares a device or URL, there's no visual indication of whose photos are playing. User A might watch for an hour, confused about why they don't recognize the photos, not realizing they're viewing User B's slideshow.

**Prevention:**
1. **Subtle user indicator on slideshow.** A small avatar or initial in the corner (matching the logged-in user). Fades out after 5 seconds, reappears on tap/interaction.
2. **Settings page shows current user.** "Logged in as sam@gmail.com" with logout button.
3. **URL structure clarity.** If feasible, `okno.moonacle.com/sam` vs `okno.moonacle.com/wife` so the URL itself indicates the user.

**Which phase should address it:** Multi-user UX polish phase.

## "Looks Done But Isn't" Checklist

Things that will pass basic testing but fail in production multi-user scenarios.

- [ ] **Token isolation test:** User A and User B both authenticated. Verify User A's proxy requests use User A's token (not B's). Must test with TWO different Google accounts simultaneously.
- [ ] **Cache isolation test:** User A has 100 photos, User B has 200 photos. Verify User A's slideshow never shows User B's photos and vice versa. Run both slideshows for 30+ minutes.
- [ ] **Config isolation test:** User A sets interval to 10s, User B sets interval to 60s. Verify each user's slideshow uses their own interval, not the other's.
- [ ] **Session regeneration test:** Verify session ID changes after OAuth login by inspecting `Set-Cookie` headers before and after auth.
- [ ] **Refresh token persistence test:** User authenticates, wait 2 hours (access_token expires), verify slideshow still works (refresh_token used to get new access_token).
- [ ] **Concurrent refresh test:** Both users' baseUrl refreshes fire simultaneously. Verify no cross-contamination and no crash.
- [ ] **Invite code one-time-use test:** Redeem a code, try to redeem it again. Must fail.
- [ ] **Logout isolation test:** User A logs out. User B's slideshow must continue working (User A's logout must not clear User B's session or tokens).
- [ ] **Migration test:** Existing `tokens.json` and `cache.json` data migrated as first user. Verify all photos still work. Then add a second user. Verify first user's photos are unaffected.
- [ ] **Error isolation test:** User A's Google account revokes app permission. Verify User A sees appropriate error but User B's slideshow is completely unaffected.
- [ ] **Stale baseUrl test:** Don't refresh User A's baseUrls for 61 minutes. Verify the slideshow handles expired URLs gracefully (shows next photo instead of error screen).

## Recovery Strategies

### If Cross-User Data Leak Is Discovered Post-Deploy

1. **Immediate:** Take the server offline (PM2 stop). Prevent further leakage.
2. **Assess:** Check logs for which users' data may have been exposed. Look for `Authorization: Bearer` tokens in access logs -- if tokens were swapped, the logged token doesn't match the logged userId.
3. **Notify:** Inform affected users that their Google Photos metadata may have been visible to other users. (Photos themselves are hosted by Google and not stored on your server -- the leak is metadata, thumbnails, and viewing access, not photo files.)
4. **Fix:** Deploy the per-user isolation fix.
5. **Verify:** Run the full "Looks Done But Isn't" checklist above.
6. **Reset:** Force all users to re-authenticate (rotate session secret).

### If Migration From JSON to DB Fails Mid-Deployment

1. **Rollback:** Restore `tokens.json`, `cache.json`, `config.json` from the `.bak` files created during migration.
2. **Revert:** Deploy the previous version of the code (git revert to pre-migration commit).
3. **Investigate:** Check migration script logs for the specific failure point.
4. **Re-attempt:** Fix the migration script, test against a copy of the production JSON files, then re-deploy.

### If Google Revokes OAuth Consent for All Users

This can happen if Google detects policy violations or suspicious activity.

1. **Check email.** Google sends notification to the project owner's email.
2. **Review Google Cloud Console.** Check OAuth consent screen status and any enforcement notices.
3. **Re-apply:** If the revocation was automated and incorrect, appeal through the Google Cloud Console.
4. **Communicate:** Let users know their slideshows will be down until OAuth is restored.
5. **No data loss.** Cached photo metadata is still in the DB. Once OAuth is restored, users just need to re-authenticate (not re-select photos) IF their Picker sessions are still valid.
